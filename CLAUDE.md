# steamworks.js — community edition

This is the community-maintained fork of [ceifa/steamworks.js](https://github.com/ceifa/steamworks.js): native Node.js bindings for the Steamworks API, built on [steamworks-rs](https://github.com/Noxime/steamworks-rs) and [napi-rs](https://napi.rs), aimed at Electron and Node games. Upstream went quiet around late 2025; this fork merges the reviewed-but-abandoned upstream PRs and continues development. It is published as `@jdeffner/steamworks.js` and installed as a **drop-in replacement** via npm alias:

```
npm i steamworks.js@npm:@jdeffner/steamworks.js
```

That drop-in promise is the one thing we can never compromise on. Games depending on `steamworks.js` must be able to switch to this fork with zero code changes. Existing exported names, signatures, and behaviors are frozen; new API is additive only.

## A small glossary

- **upstream** means ceifa/steamworks.js, the original repo this forked from.
- **the fork** means JDeffner/steamworks.js, this repo.
- **steamworks-rs** means the Rust crate wrapping the Steamworks C++ SDK. We pin a git rev of it in `Cargo.toml`; it vendors the Steam SDK headers itself.
- **the native module** means the Rust cdylib compiled per platform to `dist/<platform>/steamworksjs.*.node`.
- **client.d.ts** means the TypeScript surface of the native module, generated by napi during the build. Committed, never hand-edited.
- **the alias install** means `npm i steamworks.js@npm:@jdeffner/steamworks.js` — how users get the fork under the upstream name.
- **a cherry-pick** means porting an unmerged upstream PR into the fork, preserving the original author in the commit.

## How it works

`index.js` is the JS entry: it picks the prebuilt `.node` binary for the current platform, wraps `init()` to start a 30 Hz `runCallbacks` interval, and adds the Electron overlay helper. Everything else is Rust in `src/`:

- `src/lib.rs` — `init`/`restartAppIfNecessary`/`runCallbacks`, exports `api`.
- `src/client.rs` — the global `steamworks::Client` singleton (`crate::client::get_client()`).
- `src/api/*.rs` — one module per Steam interface (`workshop`, `matchmaking`, `overlay`, `stats`, `cloud`, `input`, …), each a `#[napi] pub mod` registered in `src/api/mod.rs`. Rust `snake_case` becomes JS `camelCase` automatically.

Patterns to copy when adding bindings (read a neighboring module first, e.g. `matchmaking.rs`):

- Sync calls: fetch the client with `crate::client::get_client()`, call through, map errors with `napi::Error::from_reason`.
- Async Steam callbacks: `tokio::sync::oneshot` channel — Steam's callback sends into `tx`, the `#[napi] pub async fn` awaits `rx`. Never block; callbacks are pumped by the JS-side interval.
- 64-bit values (SteamId, lobby ids, handles): always `BigInt`, never `f64`/`number` — JS numbers silently lose precision above 2^53.
- Enums crossing the boundary get their own `#[napi]` enum plus an explicit `match`/`From` mapping; don't leak steamworks-rs types into the public surface.

## Building and verifying

- `npm ci` once, then `npm run build:debug` — compiles the Rust module for your platform (~30 s warm) and regenerates `client.d.ts`. This is the main dev loop.
- `npm run build` — release build plus `index.d.ts` generation from `index.js` JSDoc. Use before a release, not for iteration.
- The TypeScript smoke test is the integration check: `cd test/typescript && npm i && npm run compile`. It compiles real usage of the whole typed surface with `--strict`; run it after any API change.
- CI (`.github/workflows/`) enforces `cargo fmt --all --check` and `cargo clippy`, builds all four platforms, and runs the smoke test. Run `cargo fmt` and `cargo clippy` locally before pushing — a fmt diff is the most common avoidable CI failure.
- After a build, `git status` should show either a clean tree or an *intentional* `client.d.ts` diff that matches the API you added. An unexpected diff there means you changed the public surface without meaning to.
- You cannot actually talk to Steam in CI or on a dev box without the Steam client running and a real app id. `require('steamworks.js')` loading the binary plus the smoke test compiling is the verification bar; the scripts in `test/*.js` are manual harnesses for a machine with Steam running. Don't write tests that need a live Steam client to pass.

## The ways to hurt yourself

1. **Hand-editing generated files.** `client.d.ts` is written by the napi build; `index.d.ts` comes from `npm run types` off the JSDoc in `index.js`. Edit the Rust or the JSDoc, rebuild, and commit what falls out. A hand edit will be silently reverted by the next build.
2. **Breaking the drop-in contract.** Renaming an export, changing a signature, or making an optional argument required breaks every game using the alias install. Additive changes only; new parameters get defaults matching old behavior (see `workshop.createItem`'s `fileType` defaulting to Community).
3. **`number` where a `BigInt` belongs.** Steam ids and handles are u64. Passing them through `number` corrupts them for ids above 2^53 and works fine in every quick test.
4. **Forgetting the redistributables.** The Steam runtime libraries in `sdk/redistributable_bin/` must match the steamworks-rs SDK version. When bumping steamworks-rs, refresh those binaries from the matching SDK; a mismatch fails at runtime on users' machines, not at build time.

## Conventions

- Conventional commit titles, plain language: `feat(stats): leaderboard bindings`, `fix(workshop): …`.
- When porting an upstream PR, keep the original author's commit authorship; the release notes credit the upstream PR number.
- JS in `index.js` uses 4-space indent and JSDoc types (this file *is* the type source for `index.d.ts`). Rust follows whatever `cargo fmt` says.
- New public API gets a JSDoc/doc-comment line, ideally linking the Steamworks docs page like the existing bindings do.
- Never open a PR, publish to npm, or push tags unless explicitly asked. Releases: bump `package.json` version, tag `v*`, and the Publish workflow builds all platforms; npm publish is manual by the maintainer.
- Don't commit plans, scratch notes, or agent working files. The repo is the product; this file, the README, and `wiki/` are the docs. The `wiki/` directory is the source of truth for the GitHub wiki — a workflow syncs it on push to main; never edit the GitHub wiki directly, and update the relevant `wiki/` page when you change public API.

## Roadmap

- **Phase 1 (shipped, v0.5.0):** steamworks-rs 0.12.1 upgrade, `createItem` fileType, cloud timestamps/persistence checks, permanent workshop deletion, `returnChildren` — the reviewed upstream PRs.
- **Phase 2 (in progress):** leaderboards, friends list + rich presence, lobby list filters, controller input glyphs. All primitives already exist in the pinned steamworks-rs; these are binding work, not SDK work.
- **Beyond:** demand-driven. Watch upstream issues and this repo's issues; port what real games ask for. Offer changes upstream if ceifa's repo revives.

## A note on taste

Small surface, obvious behavior. This library's users are game developers who want `steamworks.js` to feel like calling Steam directly from JS — not a framework. Bind what Steam provides, name it what Steam names it, add nothing clever in between. If a rule here fights the task in front of you, say so and get maintainer sign-off before breaking it.
